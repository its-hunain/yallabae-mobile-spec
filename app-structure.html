App Structure: Two Apps

How Customer, Seller, and Admin split across mobile apps — and why.

The structure

Customer App

Public · App Store + Play Store
  • Browsing, product detail, cart, checkout, account, wishlist, messaging
  • Built for the general public — anyone can download it

Seller + Admin App

Role-based · One app, two experiences
  • One login screen, one app — what a user sees depends on their role
  • A seller sees their store's dashboard, products, orders, payouts
  • An admin sees the full platform view — all sellers, all orders, site-wide settings
  • Distributed the same way (App Store/Play Store, or restricted access if preferred for the admin role)

Why this split

Seller and Admin are both operations tools — lists, forms, approvals, dashboards — a fundamentally different kind of app than the Customer side, which is a consumer shopping experience. Combining Seller and Admin behind role-based access means one shared codebase for both, rather than three separate apps to build and maintain, while keeping the Customer app focused purely on shopping.
ConsiderationWhy it points to 2 apps
User base sizeAdmin has effectively one user (the platform owner/team) — not worth a separate app-store listing and release cycle on its own
UI patternSeller and Admin share the same shape of screens (dashboards, tables, approve/reject actions) — Customer doesn't
ArchitectureThe seller app's foundation layer (auth, permissions) is already built to support an admin role tier — no rework needed to combine them
MaintenanceTwo codebases to update and release, not three
This is a structural decision, not a scope decision — every module in the specification (Customer, Seller, and Admin) is still built and priced exactly as documented. This only decides how many app-store listings and codebases they're packaged into.
